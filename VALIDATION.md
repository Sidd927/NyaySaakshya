# NyaySaakshya — Technical Validation (Phase B)

**Scope.** Validation of the system *behaviour* of the NyaySaakshya prototype (backend engine, API, reports) on the controlled captures the repository holds. This document does not validate marketing claims; it records what was executed, what was expected, what happened, and where the evidence stops.

**Status of this document.** Written against branch `design/landing-redesign` at commit `690d271` plus the uncommitted Phase A UI wording edits, the **Phase B.2 controlled fixes** and the **Phase B.3 semantic closure** and the **Phase B.4 acceptance decisions** (committed at the end of B.4 as the validation baseline). Phase B (original findings), Phase B.1 (root-cause investigation) and Phase B.2 are preserved below as the *previously observed defect* record; results that B.2 or B.3 changed are marked **(B.2)** / **(B.3)** with the old value kept beside the new one. Everything marked **executed** was run and can be re-run with the commands in [§9](#9-reproducibility-package). Items marked **cited** were taken from committed project artefacts and were not re-executed unless stated.

**Headline.** Phase B found three defects that affected public claims: `SEC-PLAIN-002` asserting "no TLS" on truncated and fragment streams (D1), non-email traffic graded STRONG 100 (D2), and an evidence state, INCOMPLETE, that nothing produced (D3). Phase B.2 fixed all three in the evidence layer and the coverage rule. B.2's own verification then found D7: a capture cut inside the TLS handshake still graded STRONG 100 because a partial configuration checklist counted as a positive conclusion. **Phase B.3 closed D7 at the semantic layer** (a partial result is never a conclusion), found and fixed four defects of the same class, made the score contract machine-readable (`scored`, `value: null` when withheld), made the assessment ID cover the analyser and the outcome, and measured that the ML lane cannot change a security conclusion on any of the 98 captures. No scoring constant, threshold or weight was changed in any phase. See [§14](#14-phase-b3-semantic-closure) for the B.3 record and its remaining limitations.

## 1. Method and independence levels

Every result answers: what was tested, what was expected, what happened, why the result is considered correct, what evidence supports it, what limitation remains. A result is **PASS** only when its expectation comes from something other than the engine's own output. Expectations are classified by how independent they are:

| Level | Source of the expectation | Independent of the engine? |
|---|---|---|
| **I-A** | Constructed: a real Postfix/Dovecot server configured and driven by a scripted client (`research/experiments/oq33r`) | Yes (software we did not write) |
| **I-B** | Per-stream generation labels written to a sidecar the engine never sees (`ground_truth.json`, `manifest.json`) | Yes, but the generators are **synthetic and authored in this project** |
| **I-C** | Raw-byte wire facts read straight from tshark with plain regexes, sharing no extraction logic with the engine | Yes for logic; shares tshark itself |
| **I-D** | Definitions in the project's own rule source and published scoring constants | Independent *recomputation*; the specification itself is the project's |
| **I-E** | Expected values *generated by the pipeline* (`demo/expected/*.json`) | **No.** Regression baseline only; never counted as a PASS on its own |

Two layers:

* **Layer 1 (extraction).** Does the engine read the packets correctly? Every TCP stream is read independently with `tshark -z follow,tcp,raw` and compared field by field with the engine's evidence.
* **Layer 2 (verdicts).** Do findings and scores respect labels, wire facts and the engine's own rules? Invariants were **pre-registered** in `label_check.py` before verdict-level results were inspected. Three of them were mis-specified and were corrected openly; the first-run numbers are kept in [Appendix B](#appendix-b--expectations-revised-during-validation). No expectation was changed because an engine result was inconvenient (the one result that contradicts the engine, INV-6, was **not** revised).

Statuses: **PASS**, **PARTIAL**, **FAIL**, **NOT TESTED**, **NOT APPLICABLE**. "Not tested" is never converted into a pass.

## 5. Detailed results

### 5.1 Evidence extraction accuracy

For every one of the 1,426 TCP streams, `oracle_check.py` reassembles the stream with `tshark -z follow,tcp,raw`, takes the server side as the end on a well-known mail port, and decides four facts with plain regular expressions (STARTTLS/STLS offered; STARTTLS/STLS command sent; cleartext AUTH/LOGIN/USER/PASS before any TLS record; ServerHello version from tshark's TLS dissector). It never sees an evidence state, a session or a rule.

| Fact | Agree | Disagree | Distribution in the oracle |
|---|---:|---:|---|
| Advertised | 1426 | 0 | True 965 / False 461 |
| Requested | 1426 | 0 | True 734 / False 692 |
| Cleartext auth | 1426 | 0 | True 551 / False 875 |
| TLS version | 1423 | 3 | 1.0 ×26, 1.1 ×23, 1.2 ×265, 1.3 ×490, none ×622 |

Agreement is not trivial: every fact takes both values in volume. The 3 disagreements are `p11cert/tls12_*.pcap`, raw TLS 1.2 on a non-mail port, where the engine identifies no protocol and extracts no version. Phase B treated this as a defect (D2); since B.2 the engine states that no supported protocol was identified and withholds the posture, so the disagreement is a scope difference (the oracle reads TLS on any port). Re-executed after B.2: still 1426/1426/1426/1423. **Limit:** agreement is measured on synthetic generator traffic with fixed dialects plus 13 real-vendor streams; it says nothing about vendors or dialects not in the corpus. The oracle shares tshark's reassembly and TLS dissector with the engine.

### 5.2 The six evidence states

Census over all 17,112 field observations after Phase B.2: OBSERVED 9,052 · UNKNOWN 4,483 · NOT_OBSERVABLE 1,995 · INFERRED 975 · AMBIGUOUS 340 · **INCOMPLETE 267**. (Phase B: OBSERVED 9,092 · UNKNOWN 4,710 · INCOMPLETE 0. Net movement: −40 OBSERVED and −227 UNKNOWN, +267 INCOMPLETE.) All six states are now produced by real captures, and `test_all_six_evidence_states_are_produced_by_real_captures` pins it. One real example per state, with the engine's own basis text:

| State | Capture · field | What the capture contains | System output | Why appropriate | An incorrect classification would be |
|---|---|---|---|---|---|
| OBSERVED | `scene_b` · TLS version | TLS 1.3 ServerHello, frame 6, with `supported_versions` | `TLS1.3`, frame 6, "ServerHello supported_versions extension (authoritative for TLS 1.3)" | The value is literally in the bytes | INFERRED, or a version the bytes do not contain |
| INFERRED | `scene_b` · forward secrecy | same session, no explicit statement of PFS | `true`, frame 6, basis "RFC 8446 §1.2 and App. D.5: TLS 1.3 removed static RSA and static Diffie-Hellman…" | Deduced from an observed version plus a cited rule | OBSERVED (the bytes do not say it) |
| UNKNOWN | cleartext IMAP · cipher suite | No TLS at all | `null`, "no ServerHello observed" | Nothing to read | `false`, or "weak cipher" |
| AMBIGUOUS | `postfix_smtp_no_starttls_offered` · advertisement | Capability response without STARTTLS | `false`, frames 10/12/14, "genuine non-support and upstream stripping are indistinguishable here" | Two readings produce identical bytes | "stripped" (an attack claim) or "secure" |

### 5.3 NOT_OBSERVABLE is not "invalid"

* 1,687 findings carry status NOT_OBSERVABLE (Phase B: 1,647; B.2 adds 40 `SEC-CFG-001` entries where no checklist item could be evaluated); all are severity INFO. The model enforces that a non-assertive status cannot carry a higher severity (`SecurityFinding.__post_init__`).
* After removing the sentences that *negate* the failure reading (6 distinct texts), no NOT_OBSERVABLE finding text contains invalid, untrusted, forged, expired, compromised or weak. The engine says so explicitly: "absence of certificate evidence is not evidence of an absent, invalid or untrusted certificate."
* No capture has a NOT_OBSERVABLE finding, no OBSERVED_ISSUE, and a non-zero penalty (SC-3, 98/98).
* End to end: `scene_b` (TLS 1.3 IMAPS) has 4 NOT_OBSERVABLE and 4 OBSERVED observations and scores STRONG 100.0. This is correct under the stated design and was the subject of the Phase-A clarification: "The certificate was not observable in this TLS 1.3 session; no certificate fault was therefore established." **STRONG here means "no fault established", not "the certificate was verified".**
* One related design fact the reader must keep: the score deliberately ignores observability, so a capture can be mostly NOT_OBSERVABLE and still STRONG. Coverage is reported beside the score.

### 5.8 Scoring and posture

* Formula `F2-group-damped` (`src/nyaysaakshya/posture/scoring.py`): severity weights INFO 0, LOW 3, MEDIUM 12, HIGH 28, CRITICAL 55; per-group multiplier `min(2.0, 1 + log2(n)/4)`; bands STRONG ≥ 90, ADEQUATE ≥ 75, WEAK ≥ 50, else CRITICAL; INSUFFICIENT_EVIDENCE when nothing was assessed or fewer than 50 % of sessions yielded a conclusion.
* Re-typed constants reproduce score, band and every component penalty for all 98 captures (SC-1…SC-3). The flagship arithmetic: 28×1.6462 = 46.09, 12×1.6462 = 19.75, 12×1.0 = 12.00; 100 − 77.85 = **22.15**.
* **The band name CRITICAL is a score band (< 50), not a severity.** `deepdive` is CRITICAL with no CRITICAL-severity finding (HIGH, MEDIUM, MEDIUM).
* "Assessed" means *a conclusion about the supported security posture was reached for the session* (`src/nyaysaakshya/posture/risk.py`, `build_coverage`, `_is_conclusion`). **B.3 contract:** a conclusion is an established issue, a behavioural deviation, or positive evidence from a **single-session** rule. Not conclusions, ever: an INFORMATIONAL note (B.2; Phase B mapped it to `POSITIVE_EVIDENCE`, which let D2 happen), any abstention (INSUFFICIENT_EVIDENCE, AMBIGUOUS, NOT_OBSERVABLE), and positive evidence that comes **only from the cross-session lane** (B.3). A session with no identified SMTP/IMAP/POP3 protocol is unsupported and leaves the denominator (B.2). The scoring formula, constants, thresholds and the 50 % floor are untouched. A withheld band prints "Not scored" and serialises `scored: false`, `value: null` (B.3).
* Re-execution of the committed `oq48` review (temp copy) selects the same formula; after B.2 the corpus bands moved (F2: INSUFFICIENT_EVIDENCE 0 → 2, ADEQUATE 4 → 1, STRONG 19 → 20), so the committed review is stale versus the current code (RP-10).

### 5.9 Reproducibility

| Check | Result |
|---|---|
| Two in-process runs, 98 captures | 98/98 identical assessments |
| Re-render one assessment, 5 formats | byte-identical |
| Independent re-analysis, two fresh databases, 1.5+ s apart | `assessment_id` equal on 3/3; the only differing assessment keys are `generated_at` and `run_id`; **report bytes differ in all 5 formats** |
| `force=true` re-analysis in the same database | new run IDs, same assessment ID, **same stored document** (`store_assessment` is idempotent on `assessment_id` and keeps the first document, including its `generated_at`) |

Therefore: the claim "a stored assessment always renders to the same bytes" is **verified**. The claim "the same capture re-analysed yields the same report bytes" is **false** because the analysis time is embedded; the assessment ID and body are identical. A forced re-run in the same database does *not* refresh the recorded analysis time, so a fresh upload of a known capture can display an older "analysed" time (the Phase-A session showed "Analysed 4 days ago" on a just-uploaded known capture).

`assessment_id` (**B.3 contract, schema 1.1**) identifies one analysis outcome: `SHA-256` over the capture hash, the posture schema and engine versions, the rule-set versions that produced the findings, whether the ML lane was on, the scoring formula, the band, the session counts (total / assessed / unsupported) and the issue groups (class, kind, severity, recurrence), truncated to 16 hex characters (`src/nyaysaakshya/posture/engine.py`). It excludes `run_id` and `generated_at`, and does not cover the TShark version or finding wording. **Phase B / B.2 formula** (kept for the record): `SHA-256(capture_id | schema | issue-group summary)[:16]`, which excluded every version and the outcome; §14.9 explains the defect that caused the change.

## 6. Defects and anomalies found by validation, and what Phase B.2 did about them

Phase B recorded these and fixed none of them (brief: stop and ask). Phase B.2 resolved D1, D2 and D3 and recorded a new one, D7; Phase B.3 resolved D7. For each, the **previously observed defect** record is preserved as it was written, followed by the confirmed root cause and the B.2 resolution. Two statements in the Phase B text were imprecise and are corrected here: (1) protocol identification is the **TShark dissector's verdict first**, with the seven-port `MAIL_PORTS` table only as a fallback, not "a fixed port table"; (2) the Phase B "likely cause" of D2 was incomplete: three chained causes were involved (below). The original wording is kept in the D2 entry and marked withdrawn.

### D1 — `SEC-PLAIN-002` asserts "no TLS, content travelled in cleartext" on truncated and fragment streams  *(P1)*  **RESOLVED in B.2**

**Previously observed defect (Phase B).**

* **Expected.** A truncated or near-empty stream must not become a security assertion ("INCOMPLETE must not become NORMAL"; `SecurityFinding` invariant "unestablished conditions may not assert impact").
* **Actual.** 41 of 44 non-complete mail streams across 10 captures carried `SEC-PLAIN-002` OBSERVED_ISSUE MEDIUM ("the mail session carried no TLS protection … message and command content travelled in cleartext"). 30 were streams the generator labels `BENIGN_TRUNCATED` (a benign TLS upgrade cut by the end of the capture). 3 were two-frame fragments with no dialogue.
* **Reproduction (Phase B, still runnable).**
  ```bash
  tshark -r demo/captures/scene_c_no_ai_equivalence.pcap -Y "tcp.stream==0"      # frames 1–2: server banner + RST, no dialogue
  python3 research/experiments/phaseb/label_check.py                             # INV-6
  PYTHONPATH=src python3 research/experiments/phaseb/probe_counterfactual.py     # executed counterfactual
  ```
  Executed counterfactual: deleting only frames 1–2 with `editcap` moved `postfix_smtp_starttls_upgrade` from ADEQUATE 88 to STRONG 100, `dovecot_imap_starttls_upgrade` from ADEQUATE 88 to STRONG 100, and `postfix_smtp_no_starttls_offered` from 85 to 88.
* **Why it mattered.** The fragments are the capture harness's own readiness probe (`wait_port`). They changed the result of two demo captures: demo "scene C" was ADEQUATE 88.0 only because of D1 (STRONG 100.0 without the fragment) and "scene A.2" was 85.0 instead of 88.0.

**Root cause (B.1, confirmed in B.2).** The rule was not the problem; the *evidence* was. `tls_transition` was set to `OBSERVED False` ("no TLS records in this stream") whenever the TLS state was `NONE`, regardless of whether the stream contained enough to say TLS never followed. A stream that stopped after a STARTTLS request, or that held only a banner and a reset, therefore asserted an absence it had not observed. Adding `completeness == COMPLETE` to the rule would have hidden the symptom and left the same wrong evidence for every other consumer (PLAIN-002, `SEC-CFG-001`, STLS-001, TLS-001, the ML features), so the fix is upstream.

**Fix.** `session/base.py` `_absence_of_tls_evidence` decides the state of `tls_transition` when no TLS was seen:

| Case | Capture contains | `tls_transition` | Consequence |
|---|---|---|---|
| A | complete cleartext session, closed | OBSERVED False | `SEC-PLAIN-002` fires, as before |
| B | STARTTLS requested (or accepted) and the capture ends | **INCOMPLETE** | abstains; not "no TLS" |
| C | ClientHello without completion | AMBIGUOUS (unchanged) | abstains |
| D | tiny probe fragment, no client dialogue | **UNKNOWN** | nothing is asserted |
| E | closed session with an observed cleartext dialogue | OBSERVED False | fires (e.g. `F_missing_setup`) |

A session that is still open when the capture ends, with no TLS requested, is also INCOMPLETE ("TLS could still follow"). `SEC-PLAIN-002` fires only on `OBSERVED False`; `SEC-CFG-001`'s "transport protection" item now follows its delegate rule and reports NOT_OBSERVABLE instead of a failure it could not support. `SEC-PLAIN-002`'s explanation now says "the commands and any message content it carried travelled in cleartext" (it no longer claims anything about a stream with no commands).

**Result.** `SEC-PLAIN-002` OBSERVED_ISSUE: 598 → 558 across 98 captures. Of the 44 non-complete mail streams, 1 still asserts (the arguable `F_missing_setup`, Case E); the other 43 abstain. All 557 complete streams with no TLS records still fire (PF-2). Complete benign TLS ≥ 1.2: 0 of 711 flagged, unchanged (NG-1). The true-positive plaintext captures are unchanged (`postfix_smtp_plaintext_session` ADEQUATE 88, `dovecot_imap_plaintext_login` WEAK 60, deepdive CRITICAL 22.15). Demo scores moved exactly as the Phase B counterfactual predicted: scene C 88.0 → 100.0 and scene A.2 85.0 → 88.0.

### D2 — Non-email or unidentified-protocol traffic is graded STRONG 100.0  *(P0 for claim integrity)*  **RESOLVED in B.2**

**Previously observed defect (Phase B).**

* **Expected.** The README and the **published landing page** say: "A capture that shows too little is reported as insufficient evidence, never as a good grade"; the scoring module says "a capture in which nothing could be established does not score 100/STRONG"; the `oq48` re-run prints "no-evidence band = INSUFFICIENT_EVIDENCE".
* **Actual.** Seven of seven cases scored STRONG 100.0 with 8/8 observations UNKNOWN and "1/1 sessions assessed": raw TLS 1.2 with a weak RSA-1024/SHA-1 certificate, raw TLS with a good chain, raw TLS self-signed, HTTP with a cleartext password POST, FTP with cleartext USER/PASS, DNS-only, and SMTP with cleartext AUTH on port 2626 (the identical dialogue on port 25 scores WEAK 60.0).
* **Reproduction (Phase B, still runnable).** `PYTHONPATH=src python3 research/experiments/phaseb/edge_cases.py`
* **~~Likely cause (Phase B).~~** *Withdrawn as incomplete.* "Protocol identification is a fixed port table (`MAIL_PORTS` …). An unidentified stream still gets `SEC-STLS-002`/`SEC-CFG-001` … which count as a conclusion."
* **Why it mattered.** A judge uploading any non-email capture, or a real mail server on a custom port, received STRONG: a false-reassurance path that contradicted a sentence on the landing page.

**Root cause (B.1, confirmed in B.2).** Scoring is not at fault. Three causes chained: (1) there was no scope gate on the single-session lane: `reconstruct_sessions` deliberately keeps unidentified streams as transport-only sessions so nothing silently disappears, and nothing downstream asked whether the protocol was supported; (2) the rule layer therefore still emitted findings for them (`SEC-STLS-002` INSUFFICIENT_EVIDENCE, `SEC-CFG-001` INFORMATIONAL); (3) `fusion._fact_kind` mapped INFORMATIONAL to `POSITIVE_EVIDENCE` ("observed good state"), `build_coverage` counted any POSITIVE_EVIDENCE as a conclusion, so `sessions_assessed` became 1 and `compute_score` (which refuses only when nothing, or under 50 %, was assessed) returned STRONG. The weak certificate on a raw-TLS capture was never analysed at all: `_transport_only_session` hard-codes `tls_state = NONE`.

**Fix (no scoring constant, threshold or weight was changed; no unsupported-traffic score was added).**

1. **D2b, the narrow fix.** New neutral `FactKind.INFORMATIONAL` (prioritisation weight 0). An INFORMATIONAL finding is no longer POSITIVE_EVIDENCE and is not a conclusion.
2. **Supported-protocol gate.** `analysis/engine.py` `analyse_session` runs no single-session rule on a session whose `protocol` is `None`, using the existing identification (dissector verdict, port fallback) rather than a new hard-coded list.
3. **Coverage denominator.** Unsupported sessions are counted in `sessions_unsupported` and leave the denominator of the assessed fraction (`sessions_supported`). Needed so that unrelated background traffic (HTTP, DNS) next to a real SMTP session neither withholds the SMTP result nor inflates coverage (AB-7).
4. **Visible explanation.** A withheld posture prints "Not scored" and says why: "no SMTP, IMAP or POP3 dialogue was identified in this capture, so there was no supported evidence to assess" or "coverage below the floor". On the dashboard JSON, the HTML/PDF report and the workbench (headline, score table, evidence coverage, observability boundary).

**Result.** 7 of 7 non-mail cases are now INSUFFICIENT_EVIDENCE with 0/1 supported sessions assessed. A supported SMTP dialogue on port 25 is unchanged (WEAK 60.0). The deepdive is unchanged (CRITICAL 22.15).

**Remaining limitation.** This is a truth-telling fix, not a detection fix: cleartext AUTH on SMTP port 2626, or a weak certificate on a raw TLS capture, is still **not analysed**. It is reported as unsupported.

### D3 — The `INCOMPLETE` evidence state is never produced  *(P1)*  **RESOLVED in B.2**

**Previously observed defect (Phase B).**

* **Expected.** Six evidence states, including INCOMPLETE ("capture truncated at the relevant point"), demonstrated by the truncation fixtures.
* **Actual.** 0 of 17,112 field observations were INCOMPLETE. `EvidenceField.incomplete()` had no caller in `src/` (only its definition, a unit test, and consumers in `posture/model.py` and `ml/features.py`). Truncation was expressed through the separate session attribute `completeness` (COMPLETE/INCOMPLETE/TRUNCATED), and fields on truncated sessions came out as UNKNOWN or OBSERVED False.
* **Reproduction (Phase B).** `grep -rn "\.incomplete(" src` and the census in `results/evidence_states.json`.
* **Why it mattered.** "Six evidence states" is a headline claim. Five were demonstrated. It was also the upstream cause of D1.

**Implementation (the smallest producer path, not a goal of making six states appear).** INCOMPLETE ("the exchange is cut off before the outcome is known") is produced on exactly three fields, each only where a decisive reply or negotiation is missing after something was observed that should have drawn it:

* `tls_transition`, per the D1 table (Case B and an open stream).
* `starttls_accepted`: the upgrade command was observed and the capture contains no server response to it.
* `starttls_advertised` (SMTP, IMAP, POP3): a capability request was observed and its response was not.

`EvidenceField.incomplete()` carries no value, as the model requires. Session `completeness` is a separate concept and is unchanged.

**Rule interactions (audited; pinned by the rule × state tests).** INCOMPLETE yields the same class of outcome as UNKNOWN on every consumer (an abstention, never an issue), but is not blindly equal to UNKNOWN: `SEC-PLAIN-002` fires only on `OBSERVED False`; `SEC-STLS-001` keeps its INSUFFICIENT_EVIDENCE; `SEC-TLS-001` is unchanged; `SEC-STLS-002` gained an INCOMPLETE branch ("The capture ends before the capability response to a request that was observed") so that no abstention is dropped. Scoring effect: none directly; an INCOMPLETE field cannot create an issue, and the only score changes are the removals of false `SEC-PLAIN-002` findings (D1).

**Result.** 267 of 17,112 observations are INCOMPLETE across 26 captures (`starttls_accepted` 227, `tls_transition` 37, `starttls_advertised` 3). ### D7 — A capture cut inside the TLS handshake can still be graded STRONG 100  *(P1, found during B.2 verification)*  **RESOLVED in B.3**

**Previously observed defect (B.2 verification; status then: NOT FIXED).**

* **Expected.** "When the evidence is insufficient, NyaySaakshya must abstain rather than accidentally certify."
* **Actual.** `oq46/E_cut_during_handshake.pcap` (a STARTTLS request and a ClientHello, then the capture ends; completeness TRUNCATED) is graded **STRONG 100.0**, 1/1 sessions assessed. Every substantive rule abstains (`SEC-TLS-001/-002`, `SEC-STLS-001`, `SEC-KEX-001`, `SEC-FS-001` INSUFFICIENT_EVIDENCE; certificate NOT_OBSERVABLE), but `SEC-CFG-001` reports COMPLIANT "Configuration checklist: 1 of 7 items passed", and a COMPLIANT finding counts as a conclusion, so the session is "assessed" and the posture is graded. This happened identically in Phase B (STRONG 100.0 before and after B.2).
* **Root cause.** `configuration_rules._plaintext_transport` returns COMPLIANT ("TLS records were observed") whenever `tls_state` is not `NONE`, including `CLIENT_HELLO_OBSERVED` where `tls_transition` is AMBIGUOUS. One checklist item passing, with the other six unevaluated, is enough for COMPLIANT.
* **Breadth.** 24 supported sessions in 5 captures have `SEC-CFG-001` as their only conclusion: 22 complete failed-upgrade sessions (10 each in `oq36` `B07` and `C08`, 2 in `oq28` `D_failed_upgrade`) and 2 cut or incomplete sessions (`oq28/E_incomplete`, `oq46/E_cut_during_handshake`). `E_cut_during_handshake` is the only capture whose grade rests on that alone. `E_incomplete` is withheld (2/5 assessed). `B07`, `C08` and `D_failed_upgrade` are STRONG 100 (all sessions assessed) because their other sessions carry real COMPLIANT conclusions; the failed-upgrade sessions inside them count as assessed through the same checklist item, which is the same weakness at a smaller scale.
* **Why it was not fixed in B.2.** The cause is in how a partial checklist is counted as a conclusion, which borders the scoring and coverage semantics B.2 was told not to touch, and it needed an owner decision (the proposal in §13.7 was adopted in a stricter form).
* **Reproduction (B.2 state, kept).** `results/phase_b3/starting_state.json` records the B.2 behaviour of `E_cut_during_handshake` (STRONG 100.0, 1/1 assessed, `SEC-CFG-001` COMPLIANT "1 of 7 items passed").

**Resolution (B.3).** The root-cause trace, the semantic contract, the fix and its measured effect are in [§14](#14-phase-b3-semantic-closure). In one line: `SEC-CFG-001` is COMPLIANT only when all 7 items were evaluated and passed, a cross-session consistency result is not a conclusion for coverage, and the capture is now INSUFFICIENT_EVIDENCE (0 of 1 assessed, `score.value` null).

## 7. Known methodological limits

Authority is the implementation and the README "Limitations" section; additions from this validation are marked ◆.

* **No message-content analysis.** Only the protocol exchange is analysed; credential values are not extracted.
* **No decryption, keys or mailbox access.** What encryption hides is NOT_OBSERVABLE.
* **Passive and offline.** An uploaded file only; no live capture and no probing; no live mail-server connection.
* **Certificate observability.** Visible only where the handshake is in the clear (TLS ≤ 1.2); TLS 1.3 certificates are NOT_OBSERVABLE; trust and revocation are not assessed (no trust anchor, no OCSP/CRL).
* **Incomplete captures.** Truncation lowers what can be concluded. ◆ Since B.2, a stream cut off before its outcome is known is INCOMPLETE on `tls_transition`, `starttls_accepted` and `starttls_advertised`; on the other fields truncation is still expressed as UNKNOWN, and the boolean absence fields (`starttls_requested`, `auth_activity`, `plaintext_continuation`) stay OBSERVED False on a fragment. ◆ A session cut after the ServerHello can still be concluded on the negotiated parameters (`SEC-TLS-001`, `SEC-FS-001`) while completion abstains; that is deliberate (§14.4) and can grade STRONG when it is the only assessed evidence. A capture cut *before* any parameter is established no longer grades (D7, resolved in B.3).
* **No attacker attribution.** A capture cannot tell an attack from a server policy producing the same bytes.
* **No determination that fraud occurred.** The output is what the traffic does and does not show.
* **No legal chain-of-custody claim.** SHA-256 and provenance give traceability only.
* **Not a general-purpose network detector.** ◆ Enforced since B.2: a capture with no identified SMTP, IMAP or POP3 session is withheld with an explanation (D2). Protocol identification is the TShark dissector's verdict with the seven well-known mail ports as fallback, so **mail on an unrecognised port is not analysed**: it is reported as unsupported, not detected (FN-1).
* **Scope is SMTP, IMAP, POP3** including implicit TLS.
* **No authentication** in the current prototype; single analyst; the backend binds to loopback by default.
* **Prototype storage and deployment.** SQLite plus file artefacts; the Render blueprint uses an ephemeral free-tier filesystem; ◆ the frontend ships with the demo-fixture fallback enabled.
* **Optional ML lane** is off by default, bounded to re-ordering within a severity tier, and shows no independent detection value.
* **TShark-version sensitive.** The project reports score changes under TShark 4.4.x; ◆ only 4.6.8 was run here.
* **Scale untested.** Synchronous in-request analysis, one concurrent analysis by default; only small captures were exercised.
* ◆ **Controlled data is synthetic or lab-generated.** Of 98 captures, 10 are real Postfix/Dovecot traffic and 6 are real openssl handshakes; 82 are crafted by in-project generators. No real-world or third-party traffic is included.
* ◆ **Marathi is an unreviewed machine draft** for both the reports and the landing page.

## 12. Claims we must not make

* "100 % accurate", "zero false positives", or any rate. No rate has been measured on real traffic (§8). "43 of 44 non-complete streams abstain" and "0 of 711" are counts on a synthetic and lab corpus, not rates.
* "The score was improved by the fix." B.2 changed no constant; scores moved because assertions the packets did not support were removed (and 8 captures stopped being graded).
* ~~"Six evidence states are demonstrated."~~ **Withdrawn in B.2**: now claimable (ES-5, ES-10), with the qualification that INCOMPLETE is produced on three fields.
* "A capture that shows too little is *never* graded well" (unqualified). Say what is measured: nothing assessed, or under 50 % of the supported sessions assessed, is withheld. A session cut after the ServerHello can still be graded on its negotiated parameters, and a capture at exactly 50 % assessed is graded.
* "Compliant" for a capture or a session as a whole. COMPLIANT is a property of one rule's property (a version, a completed upgrade, forward secrecy, a certificate attribute); "no issue established" is the capture-level statement.
* "Detects cleartext credentials / weak certificates on any port or protocol." Mail on an unrecognised port and raw TLS are reported as unsupported, not analysed (FN-1).
* "Detects stripping attacks" or "detects attacks." It reports advertisement deviations against a control; command stripping and blind stripping are not separable (CS-4, FN-2, FN-3).
* "AI-powered fraud detection", "AI detects attacks", "AI produces the score." The ML lane has no detection the deterministic lane did not already make and cannot change a finding, the band or the score.
* "Production ready", "court admissible", "government ready", "legal chain of custody." The prototype has no authentication, ephemeral storage and one unfixed concurrency defect.
* "Works on any packet capture / general network analyser." It analyses SMTP, IMAP and POP3 only and withholds the rest.
* "Marathi reports are validated / professional." No human has reviewed them.
* "Reports are byte-identical every time." Only for the same stored assessment.
* "Tested on real-world mail traffic." The real-vendor set is 10 captures from two servers.

### 14.2 D7 root cause, traced before any change

`oq46/E_cut_during_handshake` (9 packets): SMTP greeting, `EHLO`, a capability reply that offers STARTTLS (frame 6), the client's `STARTTLS` (frame 7), then a TLS ClientHello (frame 9) and nothing more.

**A. Evidence observed.** `starttls_advertised` OBSERVED True [6]; `starttls_requested` OBSERVED True [7]; the ClientHello at frame 9; `auth_activity` and `plaintext_continuation` OBSERVED False. The session is TRUNCATED, `tls_state = CLIENT_HELLO_OBSERVED`.

**B. States.** `starttls_accepted` INCOMPLETE; `tls_transition` AMBIGUOUS (hello without completion); `tls_negotiated_version`, `tls_cipher_suite_name`, `tls_key_exchange`, `tls_forward_secrecy` UNKNOWN; `tls_certificate_chain` NOT_OBSERVABLE. Nothing is conclusive about TLS.

**C. Rules that fired.** `SEC-TLS-001`, `-002`, `SEC-STLS-001`, `SEC-KEX-001`, `SEC-FS-001`: INSUFFICIENT_EVIDENCE. `SEC-TLS-003`, `SEC-CERT-001`: NOT_OBSERVABLE. `CS-STARTTLS-001/-002`: INSUFFICIENT_EVIDENCE (no history). **`SEC-CFG-001`: COMPLIANT.**

**D. The `SEC-CFG-001` finding.** "Configuration checklist: 1 of 7 items passed." status COMPLIANT, severity INFO, with six items listed as not evaluated in `limitations`.

**E. Why 1 of 7 became COMPLIANT.** `InsecureConfigurationRule.evaluate` took the first of three branches that applies: any failing item → INFORMATIONAL; none passed → NOT_OBSERVABLE; **otherwise → COMPLIANT**. "At least one passed and none failed" was enough. The one item that passed was "transport protection", which `_plaintext_transport` passed whenever `tls_state` was not `NONE`, i.e. on a ClientHello alone, with the text "TLS records were observed".

**F. Where partial coverage became a conclusion.** `configuration_rules.py`, the final `return` of `evaluate`, and `fusion._fact_kind` mapping COMPLIANT to `FactKind.POSITIVE_EVIDENCE`.

**G. Where coverage decided "assessed".** `risk.build_coverage`: any POSITIVE_EVIDENCE fact put its session in `concluded`, so `sessions_assessed = 1`.

**H. Where the scorer received it.** `scoring.compute_score(groups, coverage)`: one group (`INSECURE_CONFIGURATION`, `POSITIVE_EVIDENCE`, INFO), `sessions_assessed = 1 ≠ 0`, `assessed_fraction = 1.0 ≥ 0.5`.

**I. Why that allowed STRONG 100.** The refusal path needs `sessions_assessed == 0` or a fraction below 0.5. With one "assessed" session and no penalising group, the arithmetic is 100 − 0 and the band is STRONG. The scorer behaved correctly for its input; the input was wrong.

```
capture (9 packets)
  → session            TRUNCATED, CLIENT_HELLO_OBSERVED, protocol smtp (supported)
  → evidence           accepted INCOMPLETE · transition AMBIGUOUS · version/cipher/FS UNKNOWN · cert NOT_OBSERVABLE
  → rules              TLS-001/002, STLS-001, KEX, FS: INSUFFICIENT · TLS-003, CERT-001: NOT_OBSERVABLE
                       CFG-001: "1 of 7 passed"  ──►  COMPLIANT            ◄── partial result becomes a conclusion
  → fusion             COMPLIANT → FactKind.POSITIVE_EVIDENCE
  → coverage           POSITIVE_EVIDENCE ⇒ session "concluded" ⇒ sessions_assessed = 1/1   ◄── "assessed" on a note
  → posture            no issue group, coverage 100 % ⇒ STRONG 100.0
```

**Classification.** D7 is *checklist semantics* (a partial pass reported as COMPLIANT; an item that passed on a hello) and *finding-kind semantics* (COMPLIANT counted as a conclusion regardless of how much of the property was observed), made visible by *coverage semantics* (a COMPLIANT from any lane counted as "assessed"). It is not an evidence-state defect (the states above are honest), not a fusion defect, and not a scoring defect.

A scan of the corpus (`conclusion_sources.py`, starting state) showed the same pattern was wider than the one capture: 38 sessions in 6 captures rested **only** on `SEC-CFG-001` and/or cross-session conclusions (14 of them in `C19_truncated`, a STARTTLS session cut after acceptance, through `CS-STARTTLS-001` alone).

### 14.3 The contract for COMPLIANT

The existing vocabulary is sufficient; no state was added or redefined.

| Meaning | Status in the model | Counts as a conclusion (session "assessed")? |
|---|---|---|
| **True positive conclusion**: the property was observed and established for the session | COMPLIANT (single-session rule) | **Yes** |
| **Established issue / deviation** | OBSERVED_ISSUE | **Yes** |
| **Partial observation**: some items passed, the property as a whole is not established | INFORMATIONAL (a coverage note, as the "some items failed" branch already was) | No |
| **Not observable**: structurally invisible to a passive capture | NOT_OBSERVABLE | No |
| **Incomplete / unknown**: cut off, or never seen | INSUFFICIENT_EVIDENCE (evidence states INCOMPLETE / UNKNOWN) | No |
| **Ambiguous**: more than one reading fits | AMBIGUOUS | No |
| **Consistency with other sessions** (cross-session "matches the baseline") | COMPLIANT as a finding, but **not** a conclusion for coverage | No |

A finding is COMPLIANT only if the property **named in its conclusion** is established by the evidence. It is not COMPLIANT because one checklist item passed, one field was observable, the rest was unobservable, a handshake was begun, or nothing was found.

### 14.5 Coverage semantics

**Invariant.** A session counts as assessed only through (a) an established issue, (b) a behavioural deviation, or (c) positive evidence from a single-session rule. `risk.build_coverage` / `_is_conclusion` implements it. Everything else — INFORMATIONAL, every abstention, an anomaly signal, and a COMPLIANT that comes only from the cross-session lane — does not.

Executable cases (`tests/test_semantic_contract.py`): unsupported traffic; a one-item partial checklist; an incomplete TLS handshake; STARTTLS cut after acceptance (C19); a tiny fragment; complete cleartext; complete TLS; a mixed supported/unsupported capture (the deep-dive plus 13 HTTP streams stays CRITICAL 22.15 at assessed fraction 1.0); a supported session beside an incomplete one (1 of 2 is at the floor and graded; 1 of 3 is withheld). Unrelated unsupported traffic cannot contaminate the denominator (it leaves it) or create positive evidence (the gate runs no rule on it).

### 14.8 Machine-readable score contract

**Finding.** Until B.3 a withheld assessment published `score.value` 100.0 (when the floor withheld a capture whose issues summed to zero, e.g. C19) or 0.0 (when nothing was assessed). The dashboard printed "Not scored", but the stored assessment, the report JSON (which *is* the assessment), the run-list `score_value`, the database column, the Recent-checks list, the command palette and the downloaded-report text all carried the number. Nothing in the schema distinguished scored / not scored / unavailable / provisional. A machine consumer could not tell `100.0` (C19, withheld) from `100.0` (`scene_b`, STRONG) without also reading `overall_posture`. That is a correctness defect, and it was reachable from the UI: `reportDownload.ts` printed "Score: 100.00 / 100" for a withheld run.

**Decision (schema 1.1).** `PostureScore.to_dict` publishes `scored: bool` and sets `value: null` whenever the band is INSUFFICIENT_EVIDENCE. `value` is a score only when `scored` is true. `total_penalty` and `components` are kept: they describe the issues that were found, which is true whether or not a band could be certified (for a capture below the floor they are the established issues). The sparse-coverage `basis` text no longer embeds the arithmetic score. There is no "provisional" state: a number that is not a grade is not published. The dashboard projection also masks `value` for schema-1.0 documents already stored.

**Consumers audited.** Database `assessments.score_value` and run-list API (nullable already; now `NULL` for withheld); dashboard `score_value` / `score_text`; protocol rows; report projection ("Not scored"); HTML en/mr/both and PDF; the frontend (types made nullable; Recent checks, command palette, run selector and report download already handled `null`). Test pins updated with the schema version (`test_health`, `test_oq28_capture_produces_a_serialisable_assessment`) and documented inline. No stored document is rewritten.

**Verified.** For the 9 withheld corpus captures every JSON surface carries `null`; for three of them (D7, raw TLS, C19) the API, run list, dashboard, report JSON, HTML (en, mr, both) and PDF all agree and no `N / 100` string appears in any rendering. Graded captures still publish their number on every surface (flagship "22.15 / 100" everywhere).

### 14.9 Assessment ID contract

**What determined the ID (Phase B / B.2).** `SHA-256(capture_id | schema | issue-group summary)[:16]` where each group contributes `class:fact_kind:severity:recurrence`. Not included: engine, rule-set or TShark version; band; coverage; abstentions; evidence states; timestamps; `run_id`. The AI flag acted only indirectly (anomaly groups join the hash).

**Why 97 of 98 IDs changed in B.2, and all 98 in B.3.** The group summary changed: INFORMATIONAL findings left the `POSITIVE_EVIDENCE` group (B.2), and `SEC-CFG-001` left it (B.3). The ID did what it was built to do: the issue groups of those assessments are different. In B.2 the one unchanged ID (`E_cut_during_handshake`) belonged to a capture with no INFORMATIONAL group.

**The weaknesses found.** (a) The formula named no analyser, so (1) an engine upgrade that changed no issue group reproduced the **old ID for a new document**, and the store, which allows one document per ID, answered **HTTP 409 `ASSESSMENT_IDENTITY_CONFLICT`** when the same capture was re-analysed in an existing database (reproduced in B.3: re-analysis after a simulated engine upgrade returned 409); and (2) two assessments of one capture with equal groups but a different band or coverage (for example if only the coverage floor changed) had the same ID although their posture differed. (b) The ML flag was outside the formula: analysing a capture with the lane **on** after **off** reproduced the same ID whenever the model flagged no session (10 of 98 captures, e.g. `F_missing_setup`), and the store answered **409** again (reproduced and fixed in B.3).

**Intended contract (documented, `engine._assessment_id`).** The ID identifies **one analysis outcome**: this capture, analysed by this software, with this result. A pure function of: capture hash; posture schema and engine versions; the rule-set versions of the findings consumed; **whether the ML lane was on**; the scoring formula; the band; the session counts (total / assessed / unsupported); the issue groups. Excludes `run_id`, `generated_at`, TShark version (recorded by the pipeline, not in the ID: a documented limit), and finding wording. Same capture + same software + same configuration ⇒ same ID (tested, twice, on the flagship and on a cut capture). Different analyser, different rule-set or different outcome ⇒ different ID. A semantic engine change is *meant* to produce a different ID.

**Regression analysis before changing the formula.** Determinism (98 captures × 2): identical, unchanged. AI on/off: IDs differed on the 5 captures tested before and on 88 of 98 now (the 88 with an anomalous session, via anomaly groups); on the other 10 the AI-on and AI-off documents **shared an ID while differing in content**, which is the second weakness below, now fixed by covering the flag. The 409 scenario now returns 201 and a distinct ID (`test_reanalysis_after_an_engine_upgrade…`). Two assessments with equal groups and different band now differ (`test_assessment_id_changes_when_the_outcome_changes…`). The only artefacts that quote IDs (fixtures, sample report, landing text, evidence pack, `demo/expected`) are regenerated by `refresh_derived_artifacts.py`, which now also writes the mirrored frontend constants itself.

### 14.10 What "reproducible" means, measured (`repro_check.py`)

Flagship and `E_cut_during_handshake`, two runs each, identical configuration: capture SHA-256, evidence observations (state, value, frames, basis), findings, posture, score object, assessment ID, whole assessment except `generated_at` / `run_id`, provenance frames, and the HTML (en, mr) and JSON reports after masking timestamps: **all equal**. Same capture under a changed analyser version: **different assessment ID**, versions recorded in the document, outcome equal. So reproducible means: *same bytes + same software + same configuration ⇒ identical evidence, findings, posture, score, ID and report content, except the analysis timestamp (and `run_id`)*. Report bytes across independent analyses differ by the timestamp only. Not covered: other TShark versions (not tested), other platforms, large captures.

### 15.1 Decision: a session cut after the ServerHello

| Question | Answer |
|---|---|
| A. What property does the finding claim? | `SEC-TLS-001`: "The session negotiated TLS1.3, which meets current guidance." `SEC-FS-001` (B.3 wording): "The session provides forward secrecy." |
| B. Which kind of claim? | (1) The *negotiated parameters*: what the server selected in its ServerHello. Not (2) the security of the complete session. |
| C. ### 15.2 Decision: `SEC-CERT-004`

Behaviour, read from the rule and exercised by test: it reads one chain-wide OID list that the dissector fills with signature algorithms **and** public-key algorithm OIDs, and looks each OID up in a closed table.

| Question | Answer |
|---|---|
| False positive? | No on any observed data. An OBSERVED_ISSUE needs an OID the table lists as MD2, MD5 or SHA-1; an unrecognised OID is never reported as weak. (Theoretical: a deprecated hash OID inside RSASSA-PSS parameters; no capture contains one.) |
| False compliant? | Possible only for an algorithm outside the table in a chain that also contains a recognised current one: the unrecognised entry is not assessed. The table covers every hash the project cites as deprecated, so what could slip through is an algorithm the project has no standard for |
| Abstains when evidence is incomplete? | Yes when no OID is recognised (INSUFFICIENT_EVIDENCE) or no certificate is present (rule does not apply) |
| Caused by the parser? | Yes: the OID list is chain-level and mixes key and signature OIDs, so "an unrecognised entry" cannot be told from "an unread signature". A B.3 attempt to count unrecognised OIDs as partial flipped two real, correct captures and was reverted |
| Does the finding communicate it? | **Not before B.4**: the compliant outcome carried no limitation. It now carries the chain-level limitation the issue outcome already had |

**Decision: documented P3 limitation, not fixed.** It cannot produce a false deprecated-algorithm conclusion, it abstains without a recognised signature, and the missing information is not exposed by the parser. Only wording was added (the limitation on the compliant outcome; no new catalogue string; rules 1.4).
